# セキュリティの考え方

## anon キーをコードに書いてよい理由

`frontend/js/config.js` にはプロジェクトURLと anon キーが直接書いてある。
これは**意図したとおり**で、隠す意味がない。

- anon キーは `role: anon` の JWT で、**ブラウザに配る前提の公開識別子**
- 隠しても、通信を1回覗けば誰でも取れる
- 守っているのは鍵の秘密性ではなく、**RLS（行レベルセキュリティ）**

したがって「ハードコードされているから危ない」のではなく、
**RLSのポリシーが正しいかどうか**がすべて。

絶対にコードへ入れてはいけないのは `service_role` キー。
こちらは RLS を無視できる管理用の鍵で、漏れたら全データを読み書きされる。

## 誰が何を読めるか

| 対象 | 匿名 | ログイン済み | 本人 |
|---|---|---|---|
| 名前の一覧（ログイン画面用） | ○ | ○ | ○ |
| プロフィールの設定（体重・目標など） | ✕ | ○ | ○ |
| ワークアウトとセット | ✕ | 承認された相手のみ | ○ |
| メールアドレス（user_private） | ✕ | ✕ | ○ |

書き込みはすべて `auth.uid() = user_id` の本人のみ。

## 閲覧の承認（migration 004）

以前は `for select using (true)`、つまり**誰でも全記録を読める**設定だった。
覗き見モードのためだったが、ここでの「誰でも」はインターネット全体を指していた。
実際に、公開リポジトリの anon キーだけで全記録とメモが読める状態になっていた。

いまは `viewer_access` テーブルで管理する。

1. ログインした人が、見たい相手に申請する（`status = 'pending'`）
2. 相手が承認すると `approved` になる
3. 以降は申請なしで見られる。本人はいつでも取り消せる

判定は `public.can_view(target)` が行う。ポリシーの中から `viewer_access` を
引くと自分のポリシーに当たってしまうため `security definer` にしてあるが、
返すのは真偽値だけで、呼んだ本人の権限しか見ない。

## PINの長さ（6桁）

ログイン用のアドレスは名前の一覧から読める。つまり残る壁はPINだけ。

- 4桁 = 1万通り。1つのIPからでも数時間で総当たりが終わる
- 6桁 = 100万通り。同じ条件で数ヶ月かかる

さらに固くしたい場合は、Supabase の Authentication → Rate Limits で
`/token` の上限を下げるか、CAPTCHA を有効にする。

## 残っている弱いところ

- **ログイン済みの人なら、他人のプロフィール設定（体重・目標）は読める。**
  記録そのものは承認制だが、設定は分けていない。
  気になる場合は、設定を別テーブルに移して本人限定にする。
- **ログイン済みの人なら、種目マスターと解説を書き換えられる**
  （`exercises_update` と `guides_write` が `using (true)`）。
  共有の種目リストを全員で育てる前提のため。悪用の余地はある。
- PINの総当たりは、レート制限に依存している。上限値は Supabase 側の設定を確認すること。

## ローカル開発

`config.js` に本番の接続先が入っているため、何もしなければローカルでも本番が見える。
これを防ぐため、**localhost では自動的にダミーデータに切り替わる**（`js/demoData.js`）。
画面上部に警告帯が出る。本番を手元から見たいときだけ `?live=1` を付ける。
